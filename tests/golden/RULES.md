# Order page golden master: rule map

Generated by `tests/golden/rules.test.ts` from `tests/golden/rules.ts` and the scenario list. Do not edit by hand:
`GOLDEN_RECORD=1 npm test` rewrites it, and `npm test` fails when it is out of date.

- `npm test` runs every scenario on the current code and compares it with the recordings (any difference fails).
- `GOLDEN_RECORD=1 npm test` re-records. Only re-record from code whose behaviour is accepted as the new truth.
- Synthetic fixtures: `tests/fixtures/synthetic/` (built by `node tests/tools/build-synthetic-fixtures.mjs`), recordings in `tests/golden/synthetic/`.
- Real-data fixtures and recordings: `tests/golden/local/` (local only, never committed), extracted from the local test database with
  `node tests/tools/extract-local-fixtures.mjs` (refuses any server other than `mongodb://127.0.0.1:27099`).
- Recording format: per step, `events` (toasts that reached the screen, `window.confirm` texts and answers, requests with
  their bodies, router calls); step 1 holds the full page `state` (every row and `data-field`: value, disabled, title, min,
  options), later steps hold only the leaves that changed (`changes`). `expandStates()` in `tests/harness/snapshot.ts`
  rebuilds the full state of every step.
- A scenario that lists a rule shown by a toast, a confirm or a request (CHG-01..11, SAVE-00..17) must have an
  expectation that proves it on a step of the right kind (`EVIDENCE` in `tests/golden/rules.ts`; `npm test` checks it).
  SAVE-01 and SAVE-02 may instead be shown not firing, by a save that goes through (Admin exemption, exact-itemId lookup).
- Any `console.error` or `console.warn` during a test fails it (`tests/setup/setup.ts`): React reports missing keys, act()
  problems and hook-order changes there. The one line allowed is the page's own log of a failed order load.
- Node: jsdom 30 needs Node `^22.22.2 || ^24.15.0 || >=26` (the recordings were made on 24.21.0). `knitting/save17-server-errors`
  records V8's JSON parse error text (Node 18 words it differently); `tests/setup/setup.ts` refuses to run when it differs.
- Install: `vitest` is an optional peer of `better-auth` (a production dependency), so npm marks vitest, vite, jsdom and
  their dependencies `devOptional`, and `npm ci --omit=dev` still installs them. They are never loaded by the app; do not
  add `--omit=optional` to drop them, which also drops Next's SWC and sharp's platform binaries. A plain `npm ci` /
  `npm install` and the app bundle are not affected.

## Not covered

| Rule | What | Why |
|---|---|---|
| SRV-01 | Login token required (401/403) | Server behaviour. The mocked server copies only the two 401 answers (no token; any token other than the test token). Expired sessions, deleted users, inactive accounts (403), `?token=` and the 60 s user cache are not modelled. Proving it belongs to the server tests (SPEC S1). |
| SRV-02 | Buyer scope not applied to details or save | Server behaviour. The mocked server has no buyer filter at all, which matches what the real server does for details and save, but that is not proven here. Proving it belongs to the server tests (SPEC S1). |
| SRV-03 | The server checks no plan rule | Server behaviour. The mocked save stores whatever the page sends, as the real server does, so the harness relies on it without proving it. Proving it belongs to the server tests (SPEC S1). |
| SRV-04 | save-dates replaces the department array ($set, upsert) | Server behaviour. Ported in the mocked server: `$set` of the department array and status, and an upsert with the schema defaults. Proving it belongs to the server tests (SPEC S1). |
| SRV-05 | Plan status recalculated after a save | Server behaviour. Ported in the mocked server (recalcSingleOrder writes `Order.<dept>PlanStatus`), but the order page never shows that status. Proving it belongs to the server tests (SPEC S1). |
| SRV-06 | Server caches cleared after a save (per instance) | Server behaviour, not modelled: the mocked server has no cache, so every request reads the latest saved data. Proving it belongs to the server tests (SPEC S1). |
| SRV-07 | Rate limit and body size limit | Server behaviour, not modelled: the mocked server has no rate limit and no body-size limit. Proving it belongs to the server tests (SPEC S1). |
| SRV-08 | save-dates response and error shape | Server behaviour. The mocked server answers a save with the real 200 shape `{message, data}`; it never produces the 500 error itself (knitting/save17-server-errors scripts the error replies to test the page's handling, SAVE-17). Proving it belongs to the server tests (SPEC S1). |
